# DevSecOps Local Lab - Agent Context

## Project Overview

This is a **local Kubernetes-based DevSecOps lab** that provisions a complete secure software delivery pipeline with real enterprise tools (Jenkins, SonarQube, Harbor, DefectDojo, Argo CD, Grafana, Vault, etc.).

**Target Users**: Beginners to intermediate level wanting to learn DevSecOps practices in a safe, local environment.

## Key Information for AI Agents

### Project Type
- Local lab/learning environment (not production)
- Kubernetes-based infrastructure
- Container-native deployment
- GitOps-friendly (uses Argo CD)

### Technology Stack

| Component | Purpose | Namespace | Access |
|-----------|---------|-----------|--------|
| **k3d** | Local Kubernetes cluster | N/A | CLI-managed |

### Installation Patterns

All services follow this pattern:
```bash
cd apps/SERVICE_NAME
./install.sh
```

Each `install.sh` uses **Helm** to install from preconfigured `*-values.yaml` files.

### Key Directories

```
apps/              # Individual service deployments
  ├── jenkins/    # CI/CD pipeline
  ├── sonarqube/  # Code analysis
  ├── harbor/     # Image registry
  ├── defectdojo/ # Vulnerability tracking
  └── ...         # Other services

argocd/           # GitOps controller
static/           # Shared ingress & RBAC
jenkins/demo/     # Demo pipeline (Jenkinsfile)
```

### Important Behaviors & Constraints

1. **Docker Socket Dependency**: Project mounts `/var/run/docker.sock` for Jenkins
   - Convenient for lab
   - Not production-recommended
   - Required for image building

2. **Local-Only Architecture**: 
   - Uses k3d for lightweight clusters
   - NodePort services for local access
   - No TLS for harbor (HTTP only)
   - Insecure mode for Argo CD

3. **Beginner-Focused**:
   - README includes quick-start guides
   - Verification steps after each install
   - Troubleshooting section
   - Cleanup instructions

4. **Multi-Tool Complexity**:
   - 15+ different services to manage
   - Different namespaces for isolation
   - Various credential types (API tokens, passwords, etc.)

## Common Tasks & Guidance

### When Helping Users Install Components
- Always suggest verifying installation: `kubectl get pods -n NAMESPACE`
- Point to verification commands in the installation sections
- Recommend following the "Recommended Startup Order" for smooth setup
- Note that Vault requires `vault operator init` after installation

### When Users Report Issues
- **Pod not starting?** → Check `kubectl logs` and `kubectl describe pod`
- **Port conflicts?** → Check `lsof -i :PORT` and review install.sh
- **Credential issues?** → Verify secrets exist in Jenkins UI or Kubernetes
- **Helm failures?** → Run `helm repo update` first

### When Discussing Architecture
- Explain namespace isolation (each service in its own namespace)
- Mention ingress vs NodePort tradeoffs for local access
- Note that this is NOT production-hardened (intentionally)

### When Adding New Features
- Maintain beginner-friendly documentation
- Add verification steps
- Include troubleshooting tips
- Keep changes compatible with k3d clusters
- Consider resource requirements (8GB min, 16GB recommended)

## File Organization Guide

- `*-values.yaml` — Helm value overrides (edit before install)
- `*.yaml` — Kubernetes manifests (applied via `kubectl apply`)

### Documentation
- `README.md` — Main user guide (beginner-friendly)

## Security Reminders

⚠️ **This is a LOCAL LAB environment. Not for production:**
- No TLS by default
- Credentials in plain text during setup
- Insecure Argo CD configuration
- Docker socket mounting (security risk in production)
- Use Kubernetes Secrets or Vault for real deployments

## Quick Reference: Common Commands

```bash
# Cluster management
k3d cluster list
k3d cluster start/stop my-cluster
kubectl get nodes

# Service inspection
kubectl get pods -n NAMESPACE
kubectl logs -n NAMESPACE POD_NAME
kubectl describe pod POD_NAME -n NAMESPACE

# Helm operations
helm list -n NAMESPACE
helm uninstall RELEASE -n NAMESPACE

# Access services
kubectl port-forward -n NAMESPACE svc/SERVICE PORT:PORT

# Cleanup
k3d cluster delete my-cluster
```

## When Users Ask About...

### **Performance/Resources**
- Recommend 16GB RAM for comfortable operation
- Explain that multiple services compete for resources
- Suggest stopping unused services to free memory

### **Networking/Access**
- Explain NodePort vs Ingress (NodePort for local, Ingress for routing)
- Help with port-forwarding for services without NodePort
- Clarify local DNS setup (localhost vs .local domains)

### **Adding New Tools**
- Guide them to follow the same pattern: chart → values.yaml → install.sh
- Remind about namespace isolation
- Verify resource requirements

### **Production Use**
- Strongly recommend against using this setup in production
- Suggest using managed Kubernetes (EKS, GKE, AKS) instead
- Point to hardening best practices
